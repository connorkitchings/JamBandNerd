# Agent Playbook

This file stores persistent lessons and operating patterns that should survive across sessions.

## Rules

1. Treat `README.md` and `docs/user/pipeline_usage.md` as the command source of truth.
2. Preserve the `reference_date` anti-leakage boundary in any transformation or modeling change.
3. Band-agnostic core covers `ModelData`, `PredictionModel` ABC, training/eval harness, and storage contract. Collector logic stays in `data_collection/{band}/`. Per-band predictor classes are allowed in `models/{band}/` as the architecture transitions to a single model per band. See `docs/contributor/adr/0001-single-model-per-band.md` for the full decision record.
4. Prefer consolidated scripts in `scripts/` before reaching for historical or manual utilities.
5. If you change agent workflows, update `.agent/`, `README.md`, and relevant contributor docs together.

## Strategies

1. Use a small boot order and fetch docs on demand to avoid context bloat.
2. Treat `docs/logs/` as archive/history and `session_logs/` as the active session system.
3. Keep quality gates explicit and copy-pasteable so every AI tool uses the same validation path.

## Success Patterns

- Start from `.agent/CONTEXT.md`, not from broad repo search.
- Use `scripts/README.md` when reconciling which scripts are canonical vs manual/admin.
- When guidance drifts, fix the root entrypoints first and update downstream docs second.
- For freshness or orphan checks, validate only completed shows; including today or future scheduled shows creates false positives that look like ingestion failures.
- When performing database read operations for large batch verifications (e.g. checking which setlists are already ingested), always use paginated `fetch_table` wrappers instead of raw Supabase `.execute()` limits which silently truncate after 1000 rows.
- Ensure API endpoints queried by collectors include trailing slashes if the server is known to redirect to internal ports that may be unreachable.
- For live pytest suites that gate on `os.environ`, export `.env` into the shell before invoking `pytest`; app-level `load_dotenv()` hooks do not help preflight env checks that run first.
- For `uv` projects, audit the exported lockfile with `uv export --no-emit-project` plus `pip-audit`; `uvx pip-audit` on its own audits the tool environment, not the repo dependency set.
- For `uv`-managed apps with weekly security auditing, keep transitive dependency maintenance more frequent than the audit cadence. A weekly `pip-audit` paired with weekly lockfile bumps leaves avoidable red builds for known transitive fixes; run `uv` Dependabot on weekdays so lock refresh PRs usually land before the next scheduled audit.
- Keep pipeline and website Supabase credentials separate: scripts should use `SUPABASE_SERVICE_ROLE_KEY`, while the website should use `SUPABASE_ANON_KEY` and reject `sb_secret_` keys.
- Never run multiple 100-show walk-forward backtests in parallel on a single machine. Each run consumes 100% CPU for ~20 min; three in parallel triple wall time to ~60+ min via contention. Always run sequentially with a shell loop.
- In typed Next.js apps using Supabase JS, dynamic `.select()` column strings often confuse the generated parser types; prefer `select("*")` plus explicit record narrowing when the column names are runtime-driven.
- When integrating Google Stitch exports into the Next.js app, treat Stitch as visual input only: convert exports into typed components, keep data fetching server-side, and replace placeholder bands/models/routes with real repo-supported values before shipping.
- For npm workspace smoke checks, do not rely on `npm run <script> -- --list` forwarding through multiple script layers; add an explicit `:list` script so CI and local verification use the same command path.
- If `uv run` panics on macOS in sandboxed/dev-shell contexts (for example `system-configuration` NULL-object panics), treat it as an environment issue, keep `uv` as canonical in docs, and maintain a Python 3.12 `.venv` fallback path with explicitly documented validation commands.
- Before retiring a legacy codebase (e.g. Streamlit app), delete its corresponding tests first so pytest doesn't fail during collection. Run `pytest` immediately after deletion to catch any remaining import references before committing.
- When running a Next.js workspace (e.g. `npm run dev:web`) from the repository root, ensure the `.env.local` file is placed inside the workspace directory (`apps/web/.env.local`), not at the repository root, so that Next.js automatically loads it.
- For Vercel monorepo deployments, set the project root to the actual Next.js workspace (here `apps/web`) or Vercel will build from the repo root and fail with “Couldn't find any `pages` or `app` directory.”
- For Playwright smoke tests on pull requests, assume runtime secrets may be unavailable. Keep route coverage intact by accepting the app's explicit missing-env fallback state for secret-backed pages instead of requiring live Supabase data in PR CI.
- When enabling Supabase RLS on a website-backed `public` schema, do not flip tables to deny-all blindly. First map the actual anon-key read surface, remove any legacy `FOR ALL USING (true)` policies, and recreate only explicit read-only `SELECT` policies for the tables the product serves from.
- When moving a Next.js dashboard off `/` onto a dedicated route like `/predictions`, keep old root query links working with a compatibility redirect and update shared nav/link builders in the same pass; otherwise stale `/?band=...` links linger across the site.
- When backfilling a “last N replayable shows” product surface, do not rebuild exactly `N` completed shows. Use a buffered window (for example, `150` to guarantee `100`) because sparse recent shows may be intentionally skipped during scoring, and validate replay lineage per `show_date` rather than per raw accuracy row when duplicates can coexist.
- In `session_logs/`, restart numbering at `01` for each date directory. If a session ends up with several tiny follow-up entries that belong to the same content thread, prefer consolidating them into the earlier log instead of stacking redundant near-duplicate logs.

- When batch-generating historical predictions for a band with thousands of shows, export raw tables to local snapshots once (`scripts/export_backtest_snapshots.py`) and pass `--snapshot-root` to `backfill_predictions.py`. Without this, each prediction re-downloads the full setlist table from Supabase (~62k rows × N predictions), making large backfills hours-long and API-heavy for no analytical benefit.
- **DealPredictor performance ceiling**: For bands with >1,000 shows (Billy, Phish, WSP), Deal's O(n²) cooccurrence computation makes it prohibitively slow (~10 min/show). Use BillyFast/PhishFast architecture (vectorized presence matrix + LightGBM LambdaRank) which achieves seconds per show. Do not attempt to optimize within DealPredictor's inheritance chain—bypass it entirely for large catalogs.
- When hardening data ingestion, add HTTP response caching at the collector base class level (not per-band) with configurable TTL via env vars. Use a circuit breaker pattern to disable failing bands after N consecutive failures.
- ID column naming inconsistency (e.g., show_id vs api_show_id vs source_uuid) should be addressed via a formal migration strategy, not ad-hoc changes, since it affects the entire data pipeline.
- Keep band-specific exclusion filters (like WSP jam/drums) in a centralized config (config/bands.py) rather than hardcoded in model files.
- When prediction storage needs song-level SQL access, keep the run-level JSON tables as the canonical write path and add a rebuildable per-song projection; otherwise reruns with smaller `top_k` values will leave stale projected rows unless the projection is deleted and rewritten per `(band, reference_date, model_version)`.
- For destructive legacy recovery paths, clear derived outputs just-in-time for the narrow target and validate both predictions and accuracy after rebuild; this avoids wiping every downstream table up front when a later network or backtest step fails.
- In WSP audits, classify recent missing setlists before failing the band: treat upstream Everyday Companion pages without a setlist table as warnings, and reserve hard failures for collector-visible pages, request failures without fallback, or missing source metadata.
- For GitHub Actions jobs that depend on volatile upstreams, emit a machine-readable per-band outcome and degrade the affected shard instead of failing the whole workflow. Keep internal regressions as hard failures, and publish the degraded state in the workflow summary so operators can distinguish partial upstream issues from platform breakage.
- When a band has separate historical and upcoming sources, do not overload the historical shows table to drive the website's "Next Show" hero. Resolve next-show display from the upcoming source first, and keep historical rows as a fallback only when the upcoming feed is empty.
- When the pipeline publishes both next-show predictions and last-completed-show predictions, the website must not choose the most recently written row blindly. Prefer the nearest future `reference_date` for live surfaces, and only fall back to the newest historical row when no future prediction exists.
- For dynamic Supabase-backed configuration on the website (e.g. bands, models), thread fetched data as props through component layers rather than making per-component Supabase calls. A layout-level fetch + prop drilling avoids waterfall fetches while keeping the data layer server-side. Use a typed `RouteState` union (`ready | missing_env | error | empty`) consistently so every fetcher has the same error handling contract.
- When migrating hardcoded config to database-backed config in a Next.js app, keep the old config as a static fallback: if Supabase is unavailable (local dev, CI, edge), fall back to the static values so the app degrades gracefully without breaking.
- When implementing real-time features in Next.js Server Components with Supabase, use a small client-side wrapper component that listens to Supabase Realtime `postgres_changes` and gracefully calls `router.refresh()`. This silently rebuilds the server components without hydration mismatches or jarring full page reloads.
- In the website app, remove unused client islands instead of keeping “maybe later” UI code around, and scope any realtime listener to the active route keys (for example `band`, `model`, and `reference_date`) before calling `router.refresh()`. Broad subscriptions create unnecessary refresh churn and make performance issues harder to reason about.
- When integrating open social platforms like Bluesky for public data scraping, utilize the public AT Protocol endpoints (e.g., `app.bsky.feed.getAuthorFeed`) for keyless, auth-free public post retrieval instead of building a heavy scraper.
- For third-party pick-entry automations like Fantasy Goose, check the authenticated “My Picks” page before treating a missing show on the create-entry form as “no show tonight.” Some sites remove already-played shows from the create form once an entry exists, so duplicate detection must consult saved entries first.
- To eliminate awkward gaps in data tables on wide screens, avoid `table-fixed` with empty columns. Instead, use a full-width container and align metric columns (numbers, dates) to the right (`text-right`). This anchors the identifiers (songs, names) to the left and metrics to the right, making any empty space in the middle feel like natural breathing room rather than a layout bug.
- Ensure top-level navigation and control bars (for example, band selectors) are unified across routes. Use a consistent grid or flex layout for selectors so they form predictable blocks and vertically center labels alongside their button groups to maintain a professional, dashboard-grade feel.
- In Next.js 16+, `middleware.ts` is deprecated in favour of `proxy.ts` with a named `proxy` export. The proxy always runs on the Node.js runtime — `export const runtime` and `export const config` are not permitted. Do all route matching inside the function body instead of using the matcher config.
- For user-facing model evaluation dashboards, prioritize **Precision (Hit Rate)** over academic Recall. While Recall is technically more robust for coverage, users intuitively expect "Hits / Predictions" (e.g., 2/10 = 20%). When both are needed, stack them vertically with Recall as the primary bold metric and Precision as a smaller secondary "Prec" or "Hit Rate" label to maintain trust without sacrificing clarity.
- When adding HTTP User-Agent identity to data collectors across multiple bands, centralize the constant in `config.py` and reference it from each collector. Use a descriptive format like `JamBandNerd-Bot/1.0 (+https://jambandnerd.com/data-use)` that includes contact info and policy link for server admins to understand the requester's intent.
- When refactoring per-band scripts into unified `--band`/`--model` entry points, remember to clean up both `pyproject.toml` `[project.scripts]` and any docs referencing the old per-band filenames. Dangling entry points cause `pip install` warnings and mask the real canonical command.
- When adding orchestration steps that use the Supabase client (e.g., `insert`, `delete`, diagnostic queries), update any test stubs that impersonate the Supabase query builder. Stubs that only implement `select`/`execute` will fail on new code paths. Monkeypatch external diagnostic functions when the test is scoped to a different concern.
- When a collector needs multiple recent-gap fallback sources, centralize the source order in one shared resolver that returns both `(rows, source_name)`. Reuse that resolver for both diagnostics and DB insertion so source selection, hard-fail semantics, and `source` persistence cannot drift.
- After rapid multi-session development, run a deliberate steady-state review: verify `pyproject.toml` entry points match actual files, check that docs reference all (not just some) collection/model scripts, and confirm the model registry slug matches docs and CLI examples. Drift between registry slugs and documented commands is especially easy to miss.
- When adding candidate-model evaluation, centralize the historical scoring rule in shared helpers and score every target show from the prior calendar day. Otherwise backtests, comparison scripts, and training-frame generation will drift and same-day/double-header leakage will creep back in.
- For long-running fresh-trained model comparisons, add per-show progress checkpoints in the comparison loop before starting live baseline runs. Deal-style historical retraining can run for many minutes per band, and band/window logs alone are not enough to distinguish real progress from an apparent stall.
- For long-running comparison artifacts, only auto-resume partial JSON reports. Complete artifacts should be regenerated from scratch unless the user explicitly wants reuse, and partial artifacts should be written atomically after each completed band so interrupted runs always leave a valid resume point.
- The local model-test cache under `docs/reports/model_baselines/cache/` is generated resume data, not a durable report artifact. Keep that path gitignored so large cached experiment runs do not masquerade as hundreds of uncommitted source changes.
- For ablation experiments on trained models, add constructor-level overrides (not separate ablation classes) so the existing comparison framework can drive experiments unchanged. Thread overrides as `candidate_overrides: dict | None` through the comparison pipeline and store them in `experiment_metadata` for reproducibility. A single `--deal-overrides` JSON CLI arg is enough to unlock threshold, feature-subset, regularization, and weighting experiments without adding any special-case logic.
- When turning a long-running experimental comparison into a standard workflow, make the report itself decision-oriented: emit a compact readiness section plus worst-show summaries in the same artifact, then persist partial reports after each completed band so a cached run can be resumed and analyzed without a second custom script.
- When a derived table projection has both a cleanup sweep and a freshness validation, align their thresholds. A 30-day cleanup paired with a 72-hour staleness check will accumulate false-positive failures for bands without recent data. Add a reference_date window filter to the validation so only recent entries are checked, and tighten the cleanup to match.
- When rebuilding a derived projection from historical canonical rows, do not blindly reuse the canonical `predicted_at` if the derived table's timestamp is also used for freshness checks or UI selection. Either stamp a fresh projection write time during the rebuild or separate canonical generation time from derived projection freshness explicitly.
- When promoting a new model to replace an existing one, the GitHub Actions workflow is the critical path: it hardcodes model slugs and does NOT read from the registry. Metadata flag changes alone are insufficient — update the YAML directly. The local pipeline runner (`run_optimized_pipeline.py`) does use the registry, so local and CI behaviour diverge if only metadata is updated.
- Supabase table public read access must be explicitly granted via an RLS migration even when the table exists. New tables are not automatically readable by anonymous keys. Check `public_read_tables` in the latest RLS migration when adding a new data surface.
- `new Date().toISOString()` always returns UTC on Vercel. For date comparisons against naive date strings (show dates stored without timezone), use `new Date().toLocaleDateString("en-CA", { timeZone: "America/New_York" })` to get a `YYYY-MM-DD` string in Eastern time. Apply consistently to all "today" computations in the same data layer.
- When a large feature PR bundles independent fixes or infrastructure with the main change, extract them into separate branches *before* reverting. Use `git checkout -b <name> <pre-pr-commit>` to branch from the state before the problematic merge, apply only the wanted diffs, and push as standalone PRs. This avoids losing good work when rolling back.
- When reverting a merge commit, revert in LIFO order (newest PR first) and expect conflicts if later PRs built on top of the first. For `song-board.tsx`-style conflicts where a later PR depends on the change being reverted, restore the pre-merge file version rather than attempting partial resolution.
- `run_backtest.py --model deal --shows 50` is too slow to run locally for large bands (Phish, Billy, UM, WSP) because Deal retrains from scratch for each historical show (50 training runs × 400 epochs). Goose and Eggy complete in ~1 min each; the rest should be deferred to CI where they run per-band in parallel.
- When comparing live predictions to replay rows, align the semantics before debugging rankings: live prediction surfaces are keyed by the requested `reference_date`, while replay/backtest rows are keyed by `target_show_date` and usually use `reference_date = target_show_date - 1 day`. A mismatch here can look like a model bug even when both paths are internally consistent.
- `generate_model_data()` should treat `exclusion_window` as an explicit caller override. Only fall back to `BAND_EXCLUSION_WINDOWS` or `EXCLUSION_WINDOW_DEFAULT` when the caller passes no value; otherwise CLI flags and experiment overrides silently do nothing.
- For upstream API 403 failures in collectors, the fix has two layers: (1) return `[]` instead of re-raising in `_fetch_from_endpoint()` so one blocked endpoint doesn't crash the whole script, and (2) wrap `collector_func()` calls in `upsert_table()` with try/except so other tables in the same collection run can still succeed.
- For local-first historical recovery on long-running Deal `last_50` backfills, export the raw Supabase tables once to a temp snapshot root and score from those local JSON snapshots. Pair that with `LocalModelTestCache` so interrupted runs resume at the per-show level instead of re-fetching raw tables and redoing completed historical dates.
- Do not use `prediction_songs` as the durable target for historical backfills. It is a bounded latest-prediction projection with stale-row cleanup. Historical replay recovery should write canonical `predictions_{model}` rows plus `historical_prediction_runs`, `accuracy_per_show`, and aggregate accuracy.
- Future model promotion should follow a staged lifecycle instead of a one-step “turn it on” change. Keep backend readiness (`readiness_verified`) separate from website exposure (`web_promoted`), and drive the pre-platforming workflow through `scripts/model_readiness.py` so comparison evidence, local snapshot scoring, historical publish, aggregate accuracy, and readiness validation stay aligned.
- For website-facing Supabase health checks, keep narrow validators focused and compose them into one operator report. Reuse structured readiness/count metadata plus existing freshness/lineage/raw-completeness helpers instead of duplicating query logic or scraping human-readable CLI output.
- When a band's upstream API is behind Cloudflare bot protection (403 + `cf-mitigated: challenge`), add a Playwright fallback in the collector rather than trying header tricks. Use the shared `data_collection/browser.py` `CloudflareBypass` module: try standard HTTP first (fast path), fall back to Playwright on 403. Install Playwright in CI only for bands that need it (`wsp`, `eggy`). This pattern keeps collection fast when protection is lifted and resilient when it's active.
- When tightening a repo to `pytest` warnings-as-errors, audit shared singleton clients immediately. A custom Supabase `httpx` client can leave unclosed SSL sockets that only surface at suite shutdown; fix the runtime teardown and add an autouse test fixture reset in the same pass so the new warning policy stays actionable instead of flaky.
- When normalizing raw collector data, keep normalization functions in a per-band `normalizer.py` module (e.g. `data_collection/goose/normalizer.py`), not in scripts. Scripts handle orchestration only. Normalizer modules use clean package imports (`from jambandnerd.data_collection.utils import compute_source_hash`); scripts use `src.jambandnerd` path imports. WSP's `normalizer.py` is the canonical template.
- When removing a callable from a module (e.g. `save_aggregate_accuracy` removed from `rebuild_derived_data`), grep for all monkeypatches of that attribute across the test suite — they will `AttributeError` at import time even if the test is otherwise dead code.
- When removing a `dataclass` field from a shared model (e.g. `aggregate_accuracy_table` from `ModelMetadata`/`ModelDefinition`), the field propagates to at least 5 layers: the dataclass definition, the constructor call sites, the `_to_definition()` bridge, every function that reads the field, and every test fixture that stubs it. Grepping the field name alone is not enough — also grep for any helper function that exposes it (e.g. `get_aggregate_accuracy_table`) and any CLI flag that gates on it (e.g. `--skip-aggregate-check`). Treat the removal as a cascading delete: field → import → bridge → reader function → CLI flag → test fixture.
- After schema-consolidation work, run a non-archived grep for removed table and script names across `docs/`, `README.md`, `.agent/`, `src/`, and `scripts/`. The canonical docs may be updated while operator guides, frontend contracts, or package `__all__` surfaces still point at deleted storage and entrypoints.
- When two Supabase migrations share the same date prefix, Supabase applies them alphabetically. A `DROP TABLE IF EXISTS` in the second migration can destroy a table created by the first. After consolidation work, audit all same-prefixed migrations for destructive statements that target the newly created schema.
- For browser automation verification after form submission, never rely on a single immediate page check. Use a retry loop (3 attempts, 2s delay) with diagnostic logging of the post-submit page URL and body text. Wait for `networkidle` instead of `domcontentloaded` after `form.requestSubmit()`.
- If a GitHub Actions job runs Python scripts that import sibling `scripts.*` modules, treat `scripts/` as a package and invoke them with `python -m scripts.<name>` in CI. Direct file execution plus `from scripts...` imports is brittle on hosted runners, and any library imported by production workflows (for example Playwright in browser-backed collectors/automation) must live in runtime dependencies, not only the `dev` extra.
- When installing Playwright browsers and dependencies inside a virtual environment (like `uv run`) on Ubuntu CI runners, avoid single-command `--with-deps` flags. Split into an explicit `sudo uv run python -m playwright install-deps firefox` followed by `uv run python -m playwright install firefox` to bypass pseudo-TTY or isolated shell permission issues when calling package managers.
- When a promoted model needs a smaller operational replay window than the website baseline, change the registry metadata and the workflow validation path together. `validate_accuracy_tables.py` and Supabase readiness/audit checks must derive replay expectations from `readiness_windows`, or CI will keep enforcing the old default even after the workflow backtest command changes.
- For website-facing prediction audits, treat the stored canonical row as the contract. Validate `top_k` against the canonical payload length and flattened `prediction_songs` rows, not against the model registry default, because valid live predictions may emit fewer than the nominal top-k when the candidate set is smaller.
- When adding a new fallback source for a collector (e.g., PanicStream for WSP), ensure the fallback rows include every column the normalizer would produce — especially `source_hash`. The normalizer computes it, but fallback rows bypass the normalizer and go straight to `validate_and_upsert_dataframe`, which checks against the live Supabase schema.
- For `page.evaluate()` calls in Playwright, always use `async` arrow functions if the JS body contains `await`. Playwright supports async evaluate callbacks, but a plain arrow function with `await` throws `SyntaxError` at runtime with no build-time warning.
- For downstream workflows triggered by `workflow_run` on a matrix pipeline, do not gate on `conclusion == 'success'` — any single band failure fails the whole workflow. Instead, download the per-band status artifact and gate on the specific band's `prediction_action`. This isolates downstream automation from unrelated band failures.
- When a daily pipeline recomputes idempotent results from scratch, add an incremental filter before the compute loop: query the output table for already-present keys, subtract them from the target set, and only compute the delta. For accuracy backtesting, a single `IN` query on `(band, model_version, show_id)` reduces 600 daily iterations to 0–2 with no change to correctness. Keep `--no-incremental` as an explicit escape hatch for data corrections. Do NOT raise `require_results` for the "all already scored" case — that is the expected steady state, not an error.
- After removing a bottleneck, re-profile to find the new one before optimizing further. After incremental backtest reduced the backtest step from the dominant cost to ~7s, the new bottleneck for WSP (7m53s job) is Deal prediction generation at 3m37s (two training runs per band per day, ~1m45s each). Collection (Playwright) is a fixed ~3m floor for browser-dependent bands. Profile the next candidate before changing training code.
- When a DOM scraper uses a frozen profile (like ParserProfile) to encode structural assumptions, extend the validator to check content-level signals (set markers, column counts) not just table count. A validator that only checks "there are ≥N tables" will pass even when the right table has moved or changed structure, causing silent empty results. Add a page-type-specific validator (e.g. validate_setlist_page_fingerprint) called at the point of use rather than making the general validator page-type-aware.
- When a training-capable model is invoked multiple times per pipeline run for adjacent reference dates, batch the invocations into one process call that trains once and predicts for each date. Keep the single-date function signature for backward compat (thin wrapper), and expose the batched function via a multi-value CLI flag. Each date still gets its own feature-engineering call so the reference_date anti-leakage boundary is preserved.
- **Per-band Phase B model template**: New per-band models live in `src/jambandnerd/models/{band}/model.py` subclassing either `DealPredictor` (logistic) or `BandGbmPredictor` (`models/gbm/predictor.py`, LightGBM native API). Both return `List[DealPrediction]` and are compatible with the existing Deal serializer (`get_band_serializer(band)`). Register in `_BAND_PREDICTOR_CLASSES` in `models/registry.py` and add a `BandMetadata` entry to `models/metadata.py`. See `models/goose/model.py` as the canonical template.
- **Phase B promotion gate**: Candidates must improve F1@25 by at least 0.02 and must not regress p@25 by more than 0.01 across a 100-show walk-forward backtest. Legacy p@10 and r@50 deltas still gate promotion during the transition. Gate lives in `models/readiness.py:is_band_promotion_eligible`. Use `scripts/promote_phase_b_winner.py` for the final decision report.
- When incremental backtest correctly skips all already-scored shows (no new shows in the window), accuracy timestamps age past the freshness threshold. This is a false positive: the scores are immutable and correct. Gate accuracy freshness enforcement on a `backtest_incremental_all_scored` GHA output from the backtest step: when all shows were already scored and predictions are fresh, skip accuracy staleness enforcement. Prediction freshness is always enforced regardless.
- When gating downstream steps on a signal produced by sequential sub-command calls in a single workflow step, use default-true + only-write-false semantics. Write the default `true` before the sub-commands run; each call only writes `false` when it detects a condition. This avoids last-write-wins bugs when two sub-commands produce different results (e.g., notebook has new shows but deal does not). If any call writes `false`, the final value is `false`; if none write, the default `true` stands.
- When adding a workflow gate to a downstream enforcement step, check ALL upstream steps that independently validate the same condition. A gate on the final enforcement step does not help if intermediate validation steps fail independently on the same staleness condition. Each step that can exit-1 on stale accuracy needs its own gate.
- When workflow support and runtime metadata both describe the same domain concept (for example supported bands), split them into explicitly named helpers and document the ownership boundary in code, workflow comments, and docs in the same pass. Then add drift tests that pin both the workflow contract and the active docs, or the ambiguity will return.
- When the GitHub Actions workflow gains a freshness or efficiency gate, mirror the same semantics in local helper scripts instead of letting them become a separate orchestration model. Local helpers can add operator conveniences like `--force`, but prediction batching, require-output behavior, and all-scored accuracy skipping should stay aligned with the workflow.
- When cutting over a frontend from multi-model to single-model tables, use a type-driven execution order: change types first (which surfaces every broken callsite via compiler errors), then data layer, then components, then pages, then delete dead routes, then navigation, then config, then tests. This order lets TypeScript's type system act as a guardrail — every `model: ModelSlug` parameter that disappears from a type forces every consumer to update.
- When migrating Supabase queries to new tables in a Next.js app, drop the old fallback path entirely rather than keeping a dual-query strategy. The old tables may not exist on the target branch, so fallback queries will silently fail and mask real issues. A clean break with a clear `status: "empty"` fallback for missing data is more honest than a silent downgrade to stale storage.
- Align `upload-artifact` and `download-artifact` major versions across all workflows. A v7 upload cannot be read by a v8 download across workflow runs — the download silently returns "Artifact not found" and any gate that uses `continue-on-error` will silently skip downstream jobs with a green checkmark. When Dependabot bumps one action, bump its counterpart in the same PR.
- For production Supabase storage rewrites, prefer additive parallel tables over in-place mutation. Create new tables with RLS and read-only public policies, populate and validate one band first, then cut over website reads only after the new tables exist and contain validated data. Keep legacy derived tables until rollback risk is low.
- For first-band production rollouts onto new derived storage, checkpoint the tooling before writes, run empty-state checks, rehearse with dry runs, then populate model by model. Fresh-trained models like Deal need flushed per-show progress output so a slow run is observable and independently retryable.
- When a backend-only storage branch deliberately defers website cutover, restore any stale frontend reads to `main` and verify with `git diff main -- apps/web/...` before finishing. Worktree diffs against the branch may still exist because they undo earlier branch commits; the important check is that the final branch does not differ from `main` for the deferred frontend files.
- For Phase B per-band model development, do not treat empty new Supabase prediction/history tables as a blocker. Export the band's raw tables once with `scripts/export_backtest_snapshots.py`, iterate with `run_backtest.py --snapshot-root ... --dry-run --no-incremental`, and reserve Supabase `setlist_*` population for release-readiness or promotion validation.
- For large local raw-table snapshots, prefer Parquet over pretty JSON once `pyarrow` is available. Keep JSON as the portable fallback, but use manifest-recorded file paths/formats so `--snapshot-root` consumers do not need format-specific flags. This cuts disk pressure and load overhead for Phish/WSP-scale snapshots while preserving the same script contract.
- Before adding more hand-built Phase B model features, build a diagnostics pass over the exact training frame the model sees. - **New shared feature modules go under `transformations/`, not per-band**: Set-position (`transformations/set_position.py`) and co-occurrence (`transformations/cooccurrence.py`) features are band-agnostic. Per-band feature columns (e.g. `GOOSE_FEATURE_COLUMNS`) must re-include any shared features they want from the Deal core.
- **Co-occurrence features need recency weighting**: Bands like Goose have evolved their repertoire over years. Use exponential decay on `show_index` (default half-life: 80 shows) in `build_cooccurrence_matrix()` so stale patterns from old eras don't dilute recent ones. - **F1@K as primary metric alongside precision@K**: precision@25 has a hard ceiling of `min(|actual|, 25) / 25` — 72% for an 18-song show. F1@25 removes this ceiling and is already computed in `accuracy.py`. During the side-by-side transition, `BacktestSummary` carries both `dual_score` (legacy α·p@10 + (1-α)·r@50) and `dual_f1_score` (α·F1@10 + (1-α)·F1@50). The promotion gate checks F1@25 improvement + p@25 non-regression alongside legacy p@10/r@50 checks.
- **`BacktestSummary` is a frozen dataclass used across scripts and JSON serialization**: When adding fields, (1) add backward-compatible defaults in `promote_phase_b_winner.py:_load_summary()`, (2) update every construction site (`run_phase_b_backtest.py`, test helpers), (3) run the full test suite — `BacktestSummary(**data)` will fail on old JSON without the defaults.
- **For slow per-band predictors, bypass DealPredictor entirely**: When `build_cooccurrence_matrix` is the bottleneck (O(n_songs² × n_shows) Python triple loop), do not try to optimize within DealPredictor's inheritance chain. Build a standalone `PredictionModel` subclass that uses a (songs × shows) presence matrix + cumsum for all features — no cooccurrence, no per-show groupby. See `models/billy/fast_predictor.py` as the template.
- **Try LightGBM swap before adding more features**: When a logistic model plateaus, replacing it with LightGBM LambdaRank (`objective="rank_xendcg"`) on the same feature set is the highest-leverage single change. For Billy: same 7 features, LightGBM instead of LogisticRegression → +18% dual_score (0.309 → 0.366). Add features only after confirming the model form is non-linear.
- **For rolling-window diagnostics, group by outer target plus inner training target**: If a diagnostic script concatenates training frames across multiple scored target shows, do not group LightGBM queries by raw `target_show_index` alone. The same historical training target can appear in many outer windows, creating oversized duplicate query groups. Add a synthetic diagnostic group key such as `{outer_show_id}:{target_show_index}` while keeping production training groups unchanged.
- **Billy accepted baseline is V10**: `BillyFastBaselinePredictor` aliases `BillyFastPredictorV10` (`billy_fast_gbm_v10_hp_tuned`). V10 keeps the V3 feature family and applies the accepted HP tuning (`num_leaves=15`, `min_data_in_leaf=10`). V4/V5 capacity and feature expansion regressed; V6 early stopping improved recall but missed the dual-score and p@10 promotion gate. Use V10 as the base comparator for the next architecture experiment.
- **Goose fast matrix path is fast but underfit**: `GooseFastPredictor` proved the Billy-style matrix ranker can complete a 100-show Goose backtest quickly, but the first compact feature set regressed vs `goose_phase_b_v1` (`dual=0.378` vs `0.399`, `F1@25=0.255` vs `0.270`). `GooseMatrixPredictor` added cheaper Deal/set-position features and still trailed (`dual=0.377`, `F1@25=0.258`). `GooseMatrixPredictorV2` added incumbent-parity recency/history features plus selective recent-anchor co-occurrence, but quality slipped again (`dual=0.373`, `F1@25=0.250`) and runtime increased materially. Do not promote these matrix challengers; the next Goose quality attempt should start from diagnostics/ablations or the incumbent logistic path rather than more hand-added matrix features.
- **Always verify a band-specific model beats the rule-based Notebook baseline**: On Goose's 100-show window, Notebook (`plays_past_year` + `current_gap` ranking) achieves `dual=0.408, p@10=0.284`. GoosePredictor v1 (Deal-based logistic with ~30 features) scores `dual=0.399, p@10=0.265` — a net regression on precision. Before accepting any new architecture, run a fresh Notebook baseline on the same snapshot window as a floor. If the model can't beat two simple features, the extra complexity is noise.
- **Strict promotion gates do not cover every product-safe fallback**: A model can be the right operational promotion when it exactly matches a known floor and improves the active model, even if `promote_phase_b_winner.py` rejects it for missing strict +0.02 improvement thresholds. Document the gate mismatch explicitly, preserve the comparison artifacts, and treat this as a floor restoration rather than a challenger win.
- **Rank blending is not additive — test the blend before assuming it improves**: Goose GBM+Notebook rank blending with a 21-alpha grid sweep showed every alpha > 0.0 degraded performance vs pure Notebook. Even alpha=0.05 with 5% GBM weight lost `p@10 -0.004`. The GBM signal is not just unhelpful for Goose — it's toxic. When blending two rankers, run the full alpha sweep before codifying a blend class; don't assume a midpoint alpha is harmless.
- **Backtest script kwarg edge cases**: `NotebookPredictor.__init__` did not accept `**kwargs` (rejected `persist_artifacts`) and its `predict()` returns a `tuple[List, dict]` not a plain list. The backtest script at `scripts/run_phase_b_backtest.py:96` passes `persist_artifacts=False` to every predictor and expects `predict()` to return a flat iterable. Before running a new predictor class through the backtest harness, verify it accepts `**kwargs` and its `predict()` return matches what the script unwraps.
- **Vectorize before parallelizing**: When `build_training_frame` takes >300s for a band, profile the sub-components before trying to run backtests in parallel. The real wins come from (1) replacing Python loops with numpy matrix multiply (cooccurrence: 1000x), (2) replacing `iterrows()` with vectorized groupby (set_position: 37x), and (3) pre-computing date-range masks once instead of per-song (generate_deal_features: 5x). After vectorization, Billy `build_training_frame` dropped from >300s to 14s — making all 5 bands feasible in parallel.
- **Small datasets favor fewer features**: Goose ablation (13 variants, 100 shows each) showed that a 4-feature core matches a 16-feature full model (both 0.372), and the best 6-feature set (0.381) beats the 15-feature GooseFast v1 (0.378). Adding features to a small dataset (~60 training shows) hurts via GBM overfitting. When the dataset is small, ablate aggressively and keep only features with positive individual lift.
- **`plays_past_year` is not a GBM silver bullet for Goose**: Despite being Notebook's primary sort key (dual=0.408), adding `plays_past_year` to the GBM core only improves it from 0.371 to 0.372 (within noise). The GBM cannot leverage the calendar feature better than show-index windows. The gap to Notebook is architectural (GBM overfits on ~60 training shows), not feature-based.
- **Band-agnostic PhishFast architecture beats Deal/Notebook for large catalogs**: PhishFastPredictorV2 (16 features: gap, recency windows, career rate, month rate, tour/run context, rotation analytics + early stopping) beats Deal v2 and Notebook for every band tested with >1000 shows. The same architecture with different band parameters gives: Phish 0.405 (vs Deal 0.391), WSP 0.434 (vs Deal 0.408), UM 0.323 (vs Deal 0.314). Subclass PhishFastPredictorV2 for new bands — only band name and MODEL_VERSION differ.
- **Full-history training beats capped lookback windows**: The 60-show training window on Goose was a parameter choice, not a data ceiling. Training on all eligible shows (200+, gated by `reference_date` anti-leakage) improved dual from 0.378 to 0.403 — a +0.025 gain. Features already encode recency via window-play counts; the capped training window threw away 70% of available signal without adding value. Default to full-history training for all bands (using `_MIN_PLAYS` as `start_col`), and keep a `training_window_shows` parameter only for A/B comparison.
- **Notebook rank score as a GBM feature closes the rule-based gap**: Encoding Notebook's deterministic ranking as a normalized score feature (`notebook_rank_score = 1.0 - rank/(n-1)`, computed per target show) gave the GBM direct access to Notebook's signal. The model learns to blend this with its own matrix features — the result beats both (Goose 0.409 vs Notebook 0.408). This is a generalizable pattern: for any band with a rule-based baseline, encode the baseline's ranking as a feature and let the GBM decide how much weight to give it. Adding raw `plays_past_year` alone does NOT help — the encoding matters.
- **Band-agnostic experiment framework avoids class explosion**: `src/jambandnerd/models/experiment.py` provides `make_experiment_predictor` for HP sweeps (merges `_LGB_PARAMS`, replaces `_LGB_ROUNDS`/`_FEATURE_COLS`, creates unique `MODEL_VERSION`) and `ExperimentConfig`/`SweepResult` dataclasses. Per-band experiment configs and predictor subclasses live in `{band}/experiments.py`. The runner is `scripts/run_experiment.py --band <band> --sweep hp_sweep|feature_sweep [--only <slug>]`. This replaces the Billy V2-V6 pattern of permanent experiment subclasses in the predictor module. HP sweeps use `make_experiment_predictor` (dynamic); feature experiments use explicit subclasses with `ExperimentConfig.predictor_path` pointing to them.
- **Stack complementary features, don't just pick the best single one**: On Phish, `feat_notebook_rank` (dual=0.4151) and `feat_venue_run` (dual=0.4112) each beat V2 alone, but stacking them gave dual=0.4186 (+0.0138 vs V2, +0.0035 over the best single feature). When individual features target different signal dimensions (notebook_rank captures recency/ranking, venue_run captures spatial context), stacking is cheap to test and often additive. - **Never use `x or {}` with pandas objects**: `target_show_context or {}` forces `bool()` on a `pd.Series`, raising "truth value is ambiguous." When a function already handles `None` input gracefully, drop the `or {}` guard entirely — or use `x if x is not None else {}` for explicit None-checking.

- **WSP setlist sizes favor K=25, not dual p@10/r@50**: With median 21-song setlists and 68% of shows >=20 songs, precision at K=25 is the most meaningful product metric. The dual objective (0.5·p@10 + 0.5·r@50) overweights K=10 (which covers only half the show) and K=50 (which is 2.4x the median). - **When a model reaches ceiling, run per-show failure analysis before adding features**: WSP V2 plateaued at F1@25=0.3248 across 26 experiment configs (6 sweeps). Per-show failure analysis revealed that 67% of missed songs are in the candidate set but ranked below position 50 — the model gives them near-zero probability. Feature-level fixes (gap decoupling, venue-run) couldn't help because the model's shallow boosting depth (11 rounds) can't learn nuanced feature interactions. The failure analysis correctly diagnosed the problem; the lesson is that **model capacity constraints make feature engineering futile**. When a model plateaus, diagnose whether the bottleneck is features (model can't see the signal) or capacity (model can see it but can't use it) before investing in new features.
- **Sparse features (non-zero for <50% of rows) are ignored by shallow GBMs**: WSP venue-run features are non-zero only for multi-night same-venue runs (~30% of shows). With 11 boosting rounds and rank_xendcg objective, the model ignores them entirely — all 3 training configs (default ES, fixed 50 rounds, regularized) produce identical results. For sparse features to help, the model needs enough depth to create specialized branches (e.g., "IF venue_run_prior_played > 0 THEN..."). Test feature sparsity before investing in feature engineering.

The 100-show window covers ~22% of history vs WSP's ~4%, so the signal-to-noise ratio is much lower. Before porting long-window features, check the ratio of the window to total history — windows covering >10% of total shows are unlikely to carry signal.
