# GitHub Actions - Daily Pipeline

This repository runs a daily data pipeline via GitHub Actions.

## Triggers

- Scheduled: Daily at 19:00 UTC (3:00 PM ET during DST)
- Manual: `workflow_dispatch` with:
  - `band`: `all` or a single band from the dynamically discovered list
  - `skip_accuracy`: skip backtesting/aggregate accuracy for a faster run

## Overview

- Run a shared preflight step for each band to classify the collection mode and execution mode before the collector starts
- Collect raw data for selected band(s)
- Generate predictions for Notebook and CK+
- Optionally run backtests + aggregate accuracy
- Run freshness checks and write a run summary
- GitHub-hosted Python jobs install dependencies through `uv` with the checked-in `uv.lock`
- Publish per-band health states in the workflow summary (`success`, `degraded`, or `failed`)

## Notes

- Secrets required: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`; `PHISH_API_KEY` is required only for the Phish collector.
- Manual runs of `daily-pipeline.yml` now build the matrix only for the selected band instead of creating skipped jobs for every band.
- The workflow now runs `scripts/collection_preflight.py` for every band and records both the policy mode (`always_refresh`, `window_refresh`, `verify_only_when_idle`) and the selected execution mode (`full_refresh`, `bounded_refresh`, `verify_only`) in the run artifacts and monitoring summary.
- Current policy defaults are intentionally conservative: Goose and Eggy remain daily full-refresh collectors; Billy Strings, Umphrey's McGee, Phish, and WSP remain daily bounded/window collectors.
- For WSP, the workflow installs Playwright (Firefox) to improve CI scraping reliability.
- WSP now reports a machine-readable collection outcome. Upstream blocking without recent completed-show gaps is treated as a **degraded** band run; upstream blocking that leaves recent completed-show data unusable is a hard failure.
- A degraded WSP run skips prediction/backtest regeneration and reports whether the website is reusing prior data or has to skip updates.
- The per-band freshness check uses `scripts/verify_data_freshness.py`, which only inspects completed shows and excludes today/future scheduled shows from warning logic.
- The workflow summary is generated by `scripts/generate_pipeline_summary.py`, which reuses the same completed-show window and batched Supabase lookup rules as the standalone freshness check.
- The pipeline validates prediction table freshness (`scripts/validate_prediction_tables.py`) after generation, using the latest written prediction row by `predicted_at`.
- After backtests run, the workflow validates accuracy freshness and aggregate presence with `scripts/validate_accuracy_tables.py`, using the latest `evaluated_at` rows.
- Accuracy backtesting excludes shows with 5 or fewer unique songs.
- UM now deduplicates in-memory batches by its conflict keys before upsert, and the shared upsert helper applies the same duplicate-conflict guard as a backstop.
- For manual recovery or migration workflows, use `scripts/audit_raw_data.py` before any targeted re-ingestion and `scripts/rebuild_derived_data.py` after schema changes.

## Failure Policy

- Non-WSP collection failures remain hard failures for the daily pipeline.
- WSP collector regressions remain hard failures.
- WSP upstream blocking is reported as degraded only when recent completed-show data is still usable.
- Recent completed-show setlist gaps caused by upstream blocking remain hard failures because they make downstream prediction freshness unsafe.
- The final workflow summary shows per-band health, execution mode, recent missing-setlist counts, fallback usage, and prediction handling.

## Optional Notifications

If `DISCORD_WEBHOOK_URL` is set in GitHub Secrets, the workflow posts a success/failure message with a link to the run.

## Data Validation

As of 2025-10-04, all collection scripts use **warning-only validation**:

- **Type mismatches** are logged as warnings but don't block data inserts after coercion
- **Missing required columns** and **nullable violations** fail the write
- Validation warnings appear in GitHub Actions logs for monitoring
- No `--skip-validation` flags needed in the workflow

For more details, see:
- `VALIDATION_IMPROVEMENTS.md` - Complete documentation
- `TEST_REPORT_VALIDATION.md` - Testing and verification results
