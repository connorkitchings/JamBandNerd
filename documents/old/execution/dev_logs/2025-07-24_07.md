- **Objective:** Resolve data export errors and schema mismatches to ensure the WSP data pipeline
  can perform incremental updates against the Supabase database without errors.

### Accomplishments

- **Key Outcomes:**
  - Corrected Supabase query syntax in `scrape_setlists.py` to use `.gte()` for reliable incremental
    updates, preventing unnecessary full scrapes.
  - Aligned column names in `scrape_songs.py` (`first_played`, `last_played`) with the Supabase
    database schema, resolving export errors.
  - Hardened `data_exporter.py` to handle `NaN` values by converting numeric columns to nullable
    integer types, preventing JSON serialization errors.

### Blockers & Learnings

- **Blockers Encountered:**
  - A persistent schema mismatch for the `wsp_shows` table (`year` vs. `show_year`) caused repeated
    export failures. The root cause was identified as an incorrect, hardcoded column rename in the
    `data_exporter.py` module.
  - The `wsp_setlists` data export is blocked by a missing unique constraint (`UNIQUE (link,
    song_index_show)`) in the Supabase database, which requires manual SQL execution to fix.
- **New Learnings/Patterns:**
  - This session highlighted the critical importance of verifying data transformation logic across
    the entire pipeline. A bug was found in a supposedly band-agnostic data exporter, reminding us
    that shared modules can be a source of band-specific errors if not carefully managed.
